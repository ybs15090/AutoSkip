# AutoSkip 故障排查

[返回项目首页](../README.md) · [使用指南](使用指南.md) · [识别规则](识别规则.md) · [点击与失败重试逻辑](点击与失败重试逻辑.md) · [隐私与权限](隐私与权限.md)

排查时先判断问题发生在哪个阶段：服务是否运行、Android 是否暴露候选、规则是否命中、点击是否被应用接受、点击后是否成功确认。不要只用“广告总共显示了几秒”推断点击逻辑本身的耗时。

## 快速判断顺序

```text
Shizuku 未运行或未授权
  └─ 先恢复 Shizuku 和 AutoSkip 服务

服务运行，但没有识别日志
  └─ 检查应用范围、规则和无障碍节点是否可见

日志显示命中，但没有点击注入
  └─ 检查规则延迟、候选是否在点击前消失、节点是否可操作

日志显示点击注入，但候选仍存在
  └─ 检查点击方式、倒计时限制和有限重试结果

日志显示点击已确认，但主观仍慢
  └─ 分解应用启动、广告加载、节点暴露、识别点击和页面退出耗时
```

## Shizuku 或 AutoSkip 无法启动

依次确认：

1. Shizuku 应用显示“正在运行”。
2. Shizuku 的“已授权应用”中存在 AutoSkip，且授权没有被撤销。
3. AutoSkip 首页显示自动跳过服务正在运行。
4. 使用无线调试或电脑启动 Shizuku 时，设备重启后已经重新启动 Shizuku。
5. 厂商系统没有冻结 AutoSkip 或阻止其开机广播；需要时允许后台运行，但不要授予与本项目无关的额外权限。

“开机自动恢复”只负责在条件满足时恢复 AutoSkip 服务，不能启动尚未运行的 Shizuku。页面提示环境异常时，可先使用应用内“修复”，再重新授权和启动。

## 能看到广告，但始终识别不到按钮

检查以下内容：

- 应用范围是否关闭了目标应用；严格模式下，目标应用是否已明确开启。
- 目标应用是否启用了专属规则。只要存在启用的专属规则，该应用就使用专属规则而非全局规则。
- 规则开关、匹配特征、表达式、大小写和区域是否正确。
- 按钮文字是否带动态倒计时；这类文字通常更适合“包含”或正则表达式。
- 是否能用学习模式采集到真正按钮。如果候选列表里完全没有该元素，通常说明目标尚未向 Android 无障碍框架暴露可识别节点。

Canvas、视频画面、安全窗口或部分 WebView 广告可能只把按钮画到屏幕上，而没有立即提供文字节点。主动发现任务可以更快查找已经发布的节点，但不能读取尚未发布或根本不存在的节点。

## 第一次慢、后续快，或广告仍显示约 2 秒

一次启动过程至少包含四段不同时间：

1. **应用启动与广告加载**：由目标应用、网络和广告 SDK 决定。
2. **画面显示到节点暴露**：按钮可能已经可见，但 Android/WebView 稍后才发布可访问节点。
3. **候选发现到点击注入**：由事件、主动发现、规则匹配和规则延迟决定。
4. **点击注入到页面退出确认**：由目标应用处理点击和 AutoSkip 复核共同决定。

成功日志中的：

```text
Skip click confirmed: ... attempts=1, elapsed=306ms
```

`elapsed` 从**首次点击**开始计算，只表示点击到确认结束的时间，不包含应用启动、广告加载和等待节点暴露。主动发现日志中的：

```text
Skip candidate discovered by polling: ... checks=..., elapsed=...
```

则表示主动发现开始到找到候选的时间。若要判断是哪一段慢，应把应用启动日志、候选发现/命中、点击注入和点击确认四个时间点放在一起比较。

当前版本对新前台会话进行最长 8 秒、约每 150 ms 一次的轻量文字查询，并让零延迟候选在当前事件回调中直接执行。若按钮直到第 2 秒才形成 Android 节点，AutoSkip 仍无法在节点出现前点击；这与内部额外等待 2 秒不是同一问题。

## 已命中，但点击没有生效

先查看日志是否出现 `Skip click injected`，以及最终是 `Skip click confirmed` 还是 `Skip click not confirmed`。

- **自动点击**：依次尝试当前节点、最多 4 层可点击父节点，再回退到候选中心坐标。
- **仅控件点击**：不会进行坐标回退；目标只响应真实触摸时可能无效。
- **仅坐标点击**：依赖候选边界准确；窗口缩放、横竖屏变化或悬浮层可能导致偏移。
- **规则延迟**：用户配置的延迟会被保留；节点和父节点均不可点击时，还会使用 300 ms 的准备时间。
- **应用倒计时**：有些应用会在倒计时结束前显示按钮但拒绝点击，AutoSkip 的有限重试不会也不应绕过应用内部限制。

重试间隔为 200 ms，最多点击 20 次，且首次点击后最长持续 4 秒。超过任一上限仍未确认时会放弃，避免无限连点。完整状态机见[《点击与失败重试逻辑》](点击与失败重试逻辑.md)。

## 出现误触

立即停止服务或在首页将最近误触应用加入黑名单，然后按以下顺序收紧：

1. 开启应用范围控制和严格模式，只允许必要应用。
2. 把通用的“包含”规则改成精确匹配或稳定 View ID。
3. 为目标应用创建专属规则，不让高风险规则作用于其他应用。
4. 把识别区域限制在按钮真实出现的角落或半屏。
5. 避免对短词使用忽略大小写的全屏包含匹配。
6. 优先使用控件点击；只有节点操作确实无效时才使用坐标点击。

修改后先在目标广告页重复验证，再恢复更大的应用范围。

## 专属规则似乎不见了

点击“改用全局规则”只会停用专属规则，不会删除。再次进入该应用的规则页，选择“启用专属规则”即可恢复原配置。

只有明确删除规则、恢复默认、清除应用数据或卸载且未保留数据等操作，才可能真正丢失配置。

## Android 6.0 兼容性

Android 6.0 上，`UiAutomation` 可能与其他无障碍服务产生系统级冲突：AutoSkip 启动后，其他无障碍服务可能停止，直到 AutoSkip 服务结束后才恢复。请先在非关键设备上验证，并避免同时依赖多个必须常驻的无障碍工具。

## 收集诊断日志

### 应用内导出

使用“更多”→“导出日志”，保存或发送日志文件。分享前先阅读[《隐私与权限》](隐私与权限.md)，检查包名、控件文字、时间和设备信息。

### ADB 实时日志

已连接并授权 USB 调试后，可在 Windows PowerShell 中执行：

```powershell
$autoSkipAdb = "$env:LOCALAPPDATA\Android\Sdk\platform-tools\adb.exe"
& $autoSkipAdb devices
& $autoSkipAdb logcat -v threadtime 'automator:I' 'ActivityTaskManager:I' '*:S'
```

若 `adb` 已加入 `PATH`，可直接把 `& $autoSkipAdb` 替换为 `adb`。开始记录后复现一次问题，完成后按 `Ctrl+C` 停止，并保留应用启动前后至少数秒的上下文。

> [!WARNING]
> `uiautomator dump` 会尝试创建自己的 `UiAutomation` 连接，可能与正在运行的 AutoSkip 服务冲突。确需抓取 XML 时，应先停止 AutoSkip 服务，抓取完成后再恢复；不要把 dump 失败直接判定为目标应用没有节点。

### 常见日志含义

| 日志 | 含义 |
| --- | --- |
| `accepted-no-match` | 事件通过入口检查，但当前根节点没有合法候选 |
| `accepted-match-...-via-platform-index` | 平台文本索引找到并验证了候选 |
| `Skip candidate polling started` | 新前台会话开始轻量主动发现 |
| `Skip candidate discovered by polling` | 主动发现找到了已发布的候选 |
| `Skip click injected` | Android 接受了本次节点动作或坐标注入 |
| `Skip click confirmed` | 后续复核认为原候选已经消失或窗口已切换，写入一次成功记录 |
| `Skip click not confirmed` | 达到次数或时间预算后仍不能确认成功 |

## 提交问题时请附上

- 手机品牌和型号；
- Android 版本/API 级别；
- Shizuku 或 Sui 的版本与启动方式；
- AutoSkip 版本名；
- 目标应用名称、包名和版本；
- 是否只在服务重启后的第一次出现；
- 规则特征、匹配方式、区域、延迟和点击方式；
- 可稳定复现的操作步骤；
- 从目标应用启动前到结果确认后的完整日志片段。

问题反馈入口：[GitHub Issues](https://github.com/ybs15090/AutoSkip/issues)。
